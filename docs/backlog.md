- [ ] [P1] [Bug] [→Opus] **Desktop-Sink (`paplay`): abgebrochene Wiedergabe spielt im PulseAudio-Server weiter, überlappt mit der nächsten** (Autor-Befund 2026-07-10, Desktop-Sichtprobe; Root Cause durch Sonnet reproduziert und gemessen, **kein** Fix-Vorschlag spezifiziert — braucht einen Architekturentscheid). Symptom: „Ball" (erstes Korpuswort) wird bei Wortwechsel/„Wiederholen" mehrfach hörbar, mal 1x, mal 2x, bei schnellem Wiederholen eskalierend bis 4x — **nicht deterministisch**, abhängig vom Timing. Betrifft **nicht** den zuvor gefixten Compose-Key-Bug (der bleibt korrekt, siehe abgehaktes Item unten) — dieser Bug liegt eine Ebene tiefer, im Desktop-`AudioSink` selbst.

  **Root Cause (durch Sonnet reproduziert, isoliert von Compose/Kotlin-Coroutine-Code):** `playViaPaplay` in `AudioSink.jvm.kt` geht davon aus, dass `process.destroy()` gefolgt von `waitFor()` die Wiedergabe sofort und vollständig beendet, sobald der `paplay`-Prozess tot ist. Das stimmt nicht: **PulseAudio puffert das vom Client bereits übergebene Audio serverseitig** und spielt es unabhängig vom Tod des Client-Prozesses weiter ab. Minimal-Repro außerhalb der App (reiner `ProcessBuilder`-Test gegen `core/src/jvmTest/resources/sample-thorsten-ball.wav`, volle Wiedergabe misst ~497 ms Baseline):
  1. `paplay` starten, nach 150 ms `destroy()` + `waitFor()` (Prozess bestätigt beendet).
  2. Sofort einen zweiten `paplay`-Prozess für dieselbe Datei starten.
  3. Der zweite Prozess braucht **1100–2200 ms** statt der erwarteten ~497 ms, mit sichtbar variierender Dauer über mehrere Läufe — Indiz für einen weiterlaufenden Geister-Stream des ersten Prozesses, der mit dem zweiten um denselben PulseAudio-Sink konkurriert.

  **Bereits ausgeschlossene Sackgasse:** `destroyForcibly()` (SIGKILL) statt `destroy()` (SIGTERM) probiert — macht es **nicht** besser, tendenziell eher schlechter (2150+ ms in mehreren Läufen). Das Problem liegt also nicht am gewählten Signal, sondern daran, dass **kein** Signal an den `paplay`-Prozess den zugehörigen PulseAudio-Sink-Input mitbeendet.

  **Warum das ein Opus-Punkt ist:** Es gibt mehrere plausible Fixrichtungen mit unterschiedlichem Aufwand/Risiko, keine ist im Code selbst naheliegend „die eine richtige Lösung": (a) `paplay` mit `--client-name` starten und beim Abbruch gezielt `pactl kill-client <name>` aufrufen, um den PulseAudio-seitigen Stream mit zu beenden (zusätzlicher Prozessaufruf, Abhängigkeit von `pactl` auf PATH); (b) weg von `paplay` als externem Prozess, hin zu einer Bibliothek mit echter Stream-Kontrolle (z. B. direktem PulseAudio-Binding oder zurück auf `javax.sound`, das laut bestehendem Kommentar unter WSL2 aber keine Line fand — müsste erneut geprüft werden, ob das noch zutrifft); (c) vor jedem neuen `play()` präventiv alle verwaisten Sink-Inputs killen (fragil, Seiteneffekte auf andere Audio-Quellen der Maschine). Nicht klar ohne Abwägung, welche Richtung die Aufwand/Robustheit-Balance für ein Dev-Only-Desktop-Target (ADR-0003: Desktop ist Dev-Target, keine Verifikationsplattform) rechtfertigt.

  Nicht-Ziel (vorab): keine Änderung an `PlaybackQueue`/`LernmodusScreen`/`PruefmodusScreen` (die Coroutine-/State-Ebene ist korrekt, siehe abgehakter Key-Fix) — der Fehler ist ausschließlich in `AudioSink.jvm.kt`s Umgang mit dem externen `paplay`-Prozess. Android ist nicht betroffen (`AudioTrack`, kein externer Prozess/PulseAudio).

Symptom war: Lernmodus startet → erstes Wort wird zweimal abgespielt, ab dem zweiten Wort (nach „Weiter") nur einmal.

  **Root Cause (verifiziert durch Code-Analyse, nicht mehr offen):** Beide Screens nutzen `LaunchedEffect(state)` mit dem *gesamten* Screen-State als Key, um „bei neuem Wort einmal abspielen" auszudrücken (`LernmodusScreen.kt:82`, `PruefmodusScreen.kt:107`). Der Key ist zu grob: Er koppelt das Abspielen an *jede* Structural-Equality-Änderung von `state`, nicht an den Wortwechsel. Beim Start setzt `LaunchedEffect(Unit)` **zwei** State-Variablen nacheinander — erst `recordings` (Zeile 69, löst Recomposition #1 aus), dann `state = Running(session0)` (Zeile 73, Recomposition #2). Über diese zwei dicht aufeinanderfolgenden Recompositions startet Compose den `state`-basierten Effect für dasselbe erste Wort zweimal an (der Effect für Key `Loading` wird abgebrochen und für `Running(session0)` neu gestartet, während die erste `playCurrentWord`-Coroutine schon lief) → zwei `queue.play()` auf dasselbe Wort. Ab Wort 2 gibt es nur noch **einen** State-Write pro Übergang (`advance()` setzt nur `state`), deshalb tritt das Doppeln nur beim ersten Wort auf. Das erklärt das exakte Symptom.

Derselbe Fix (Key = Karten-/Wort-Identität statt ganzer State) behebt beides.
