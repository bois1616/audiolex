# Backlog AudioLex

Stand 2026-07-07: initiales Backlog aus der Konzept-Roadmap abgeleitet, Meilensteine (M0–M5) statt Sprints. Arbeitsreihenfolge `P0` → `P1` → `P2` → `P3`. Tags: `[KLÄRUNG]` = braucht Entscheid des Autors, `[PROP]` = Vorschlag über den aktuellen Scope hinaus.

Modell-Richtwert je offenem Item (AGENTS.md §6): `[→Sonnet]` = fertig spezifiziert (Akzeptanzkriterien + Nicht-Ziele stehen im Item), direkt umsetzbar · `[→Opus]` = Architektur-/Design-Entscheid nötig · `[→Opus→Sonnet]` = erst schärfen (ACs + Nicht-Ziele ergänzen), dann umsetzen. Ohne Tag: braucht den Autor. Faustregel: Ein Item ohne ausformulierte ACs ist nie Sonnet-reif — der nächste Schritt heißt dann „schärfen", nicht „umsetzen".

## M3 – Prüfmodus + SRS

**Reihenfolge-Hinweis:** Die zwei reinen `:core`-Logik-Items (ExamSession, ReviewQueue) hängen an *nichts* und sind der nächste Sonnet-Schritt nach M2 — analog zu `LearningSession`/`PlaybackQueue` in M2, die die UI später nur noch anbindet. Der Persistenz-Spike (ADR-0004) läuft parallel/danach; erst der Prüfmodus-Screen und die Fälligkeits-Persistenz brauchen beides zusammen.

- [ ] [P1] [SRS] [→Sonnet] `ExamSession` + `ReviewQueue` als reine Logik im Paket `session`/`srs` (`:core`) — das M3-Analogon zu `LearningSession`. Kein UI, keine Persistenz (die kommt separat). Bausteine, die schon existieren: `ReviewCard` (`wordId`, `dueAtEpochMillis`, `lastRating`, `repetitions`), `ReviewRating` (AGAIN/SOON/LATER/GOOD/PERFECT), `ReviewScheduler`/`FixedIntervalScheduler` (`review(card, rating, now)` → neue `ReviewCard`; `isDue(card, now)`), `Word`.
  - AC1 (ReviewQueue): `ReviewQueue.due(cards: List<ReviewCard>, nowEpochMillis: Long): List<ReviewCard>` liefert die fälligen Karten (`isDue == true`) in stabiler, deterministischer Reihenfolge — nach `dueAtEpochMillis` aufsteigend (überfälligste zuerst), bei Gleichstand nach `wordId` als Tiebreaker (kein `Math.random`, damit Tests deterministisch sind).
  - AC2 (ExamSession, Happy Path S3): immutable Data class analog `LearningSession`, hält die fällige Kartenliste + aktuellen Index + Aufdeck-Zustand (`revealed: Boolean`, Start `false`). `currentCard: ReviewCard`, `progress`/`total`, `reveal(): ExamSession` (setzt `revealed = true`), `rate(rating, now, scheduler): RateResult` — wendet `scheduler.review` auf die aktuelle Karte an, gibt die aktualisierte Karte **und** die nächste `ExamSession` zurück (oder Ende-Signal). Nach `rate` ist das nächste Wort verdeckt (`revealed = false`).
  - AC3 (Ende): `rate` auf der letzten Karte liefert `null`/ein terminales `RateResult` (analog `LearningSession.advance()` → `null`), damit der Screen den Abschlusszustand erkennt.
  - AC4 (Leer-Zustand S4): eine `ExamSession` mit leerer Kartenliste ist entweder per `require` verboten (Screen prüft vorher via `ReviewQueue.due`) oder über einen `isEmpty`-Zustand abbildbar — Entscheidung dem Umsetzer überlassen, aber konsistent dokumentieren und testen. Empfehlung: `require(cards.isNotEmpty())` wie bei `LearningSession`, der Leer-Fall wird im Screen vor dem Erzeugen abgefangen.
  - AC5: Die aktualisierten `ReviewCard`s aus `rate` sind das, was der spätere Persistenz-Layer speichert — `ExamSession` selbst persistiert nichts, gibt die neuen Karten nur zurück.
  - Nicht-Ziele: keine Persistenz, kein UI, keine automatische Bewertungsableitung (ADR-0005 hält das bewusst draußen, `[PROP]`), kein Ease-Faktor/FSRS.
  - Tests (`:core:commonTest`, Muster `LearningSessionTest`/`FixedIntervalSchedulerTest`): ReviewQueue-Sortierung inkl. Tiebreaker + Leer-/Alle-fällig-Grenzfälle; ExamSession Happy Path (aufdecken → bewerten → nächste Karte verdeckt), Ende-Signal auf letzter Karte, `rate` liefert korrekt neu terminierte Karte (Delegation an Scheduler geprüft, nicht Intervall-Arithmetik duplizieren).
  - Verifikation: `./gradlew :core:jvmTest` grün.

Der *Entscheid* ist in ADR-0004 schon begründet (Room 2.7 + `BundledSQLiteDriver`, DataStore für Settings) — offen ist nur, ob KSP im Multi-Target-Build (android + jvm) ohne Reibung läuft.   - AC2: Eine minimale Wegwerf-Entity (z. B. `ReviewCardEntity`) + DAO + Room-Database, die auf jvm einen In-Memory- oder Datei-DB-Roundtrip macht: einen Datensatz schreiben, lesen, Gleichheit prüfen — als `:core:jvmTest`-Fall, der real gegen Room läuft (nicht gemockt).
  - AC3 (Entscheid dokumentieren): Läuft es → ADR-0004 auf `akzeptiert` setzen, Spike-Ergebnis (Versionen, KSP-Stolpersteine) in die Konsequenzen. Reibt KSP unlösbar → ADR-0004 auf `abgelöst durch SQLDelight` setzen, kurzes Folge-ADR oder Ergänzung, und diesen Spike mit SQLDelight wiederholen.   - AC4 (Nicht-Ziel): **kein** echtes Schema für Words/Sessions/Settings in diesem Spike — nur der Nachweis, dass der Persistenz-Stack im KMP-Build trägt. Das echte Schema kommt mit dem Fälligkeits-Persistenz-Item unten.

- [ ] [P1] [UI] [→Sonnet] Prüfmodus-Screen (Szenarien S3, S4, S5, S7; Gestalt: DESIGN.md „Trainings-Screens im Detail", Komponenten `RevealCard`/`RatingBar`). Voraussetzung: `ExamSession`/`ReviewQueue` (Item oben) müssen stehen; die Fälligkeits-**Persistenz** ist für einen ersten lauffähigen Screen *nicht* Voraussetzung — bis sie da ist, werden die `ReviewCard`s aus dem Korpus in-memory erzeugt (alle sofort fällig, `dueAtEpochMillis = 0`), damit S3 durchspielbar ist. Muster: `LernmodusScreen.kt` (Screen-State als `sealed interface`, `LaunchedEffect` fürs Laden, `PlaybackQueue` fürs Abspielen, `DisposableEffect { queue.stop() }` für S5). Bausteine: `ExamSession`, `ReviewQueue`, `FixedIntervalScheduler`, `createAudioSink()`, `WavFile.decode`, Korpus-Laden per `Res.readBytes` (Muster `DevPlaybackScreen`/`LernmodusScreen`). Akzeptanzkriterien:
  - Happy Path (S3): Bei fälligen Karten wird das Wort nur gehört (automatisches Abspielen bei Eintritt über `PlaybackQueue`, **kein** Text sichtbar — die verdeckte `RevealCard` in konstanter Größe, deren Silhouette die Wortlänge nicht verrät, DESIGN.md); eine große Tippfläche (die Karte selbst) deckt auf → das Wort erscheint; danach die 5 Bewertungstasten (`RatingBar`) mit deutschen Labels **und** Intervall-Hinweis (Sofort 1 min · Bald 10 min · Später 1 Tag · Gut 1 Woche · Perfekt 1 Monat, aus `ReviewRating.interval`); eine Bewertung setzt die nächste Fälligkeit (via `ExamSession.rate` + `FixedIntervalScheduler`), zeigt sie kurz bestätigend an und geht zur nächsten (wieder verdeckten) Karte. Bewertungstasten sind gleichwertig gestaltet, **keine** Ampelfarben Rot→Grün (SOUL.md/DESIGN.md: die Skala steuert Wiederholung, sie benotet nicht).
  - Reihenfolge/Aufdeck-Gate: Vor dem Aufdecken sind die Bewertungstasten nicht bedienbar (verdeckt = nur „Wiederholen"/„Aufdecken"/„Beenden"); erst nach Aufdecken erscheint die `RatingBar`. „Wiederholen" (erneut hören) muss auch im verdeckten Zustand möglich sein (das Wort nochmal hören, bevor man rät) — über `PlaybackQueue.play`, bricht laufende Wiedergabe ab.
  - Leer-Zustand (S4): Keine fällige Karte (`ReviewQueue.due` leer) → Meldung „Nichts fällig", die nächste Fälligkeit sichtbar (frühestes `dueAtEpochMillis` der Karten, menschenlesbar als relative Zeit) **und** ein Ausweg „Stattdessen Lernmodus" (Navigation zum Lernmodus-Screen) + „Zurück zum Start". Nie eine Sackgasse (DESIGN-Leitprinzip).
  - Abschluss: Alle fälligen Karten bewertet → Abschlusszustand mit Kennzahlen (Anzahl bewerteter Karten; optional Verteilung der Bewertungen) und „Zurück zum Start".
  - Unterbrechung (S5): „Beenden" jederzeit → `PlaybackQueue.stop()`, zurück zum Start; bereits abgegebene Bewertungen bleiben angewandt (die neu terminierten `ReviewCard`s liegen im Screen-State vor, bis Persistenz sie speichert); kein Pause/Resume — nächster Start ist eine neue Sitzung.
  - Audio gestört / Fehlerzustand (S7): Exception beim Laden/Abspielen → verständliche deutsche Meldung statt stillem Fehlschlag/Absturz (Muster `LernmodusScreen`, `PlaybackQueue.onError` nutzen).
  - Nicht-Ziele: **keine** Persistenz in diesem Item (Karten in-memory, sofort fällig) — die Anbindung an gespeicherte Fälligkeiten ist das separate SRS-Item darunter; kein `ChannelBadge` (M4); keine automatische Bewertungsableitung (`[PROP]`); Wortreihenfolge kommt aus `ReviewQueue.due`, kein eigenes Mischen.
  - Verifikation: `:core:jvmTest` + `:composeApp:assembleDebug` grün; Desktop-Sichtprobe (`:composeApp:run`) sobald möglich — sonst als Gerätetest-Item nachziehen (Sandbox-Skiko-Einschränkung, ADR-0003).
