- [X] [P2] [Bug] **Bluetooth hearing aid: sound only comes through after at least one manual press of the volume key** (author's finding 2026-07-18). Symptom: independently of AudioLex — with other apps too — no sound arrives over the Bluetooth link to the hearing aid until the volume key on the device has been pressed briefly at least once; after that audio plays normally. Whether this returns after a period of inactivity, the author has not checked. Author's question: can this be simulated, or a volume interaction faked programmatically, so that the app wakes the Bluetooth path itself instead of depending on the manual key press?

  To be distinguished from the already solved word-onset pre-roll bug (M1, above): that was a loss of the first milliseconds *within* a running, correctly routed playback; here the Bluetooth audio path seems to stay *entirely* mute until some volume interaction happens in the system — closer to the routing incident of 2026-07-12, documented but never fixed in code (there the route could be repaired by re-confirming the hearing aid in the Android settings, not an app bug). Open for the Opus diagnosis: whether, say, an `AudioManager.adjustStreamVolume(..., ADJUST_SAME, ...)` call or an early silence frame at app start wakes the path reliably without the author touching the hardware key — untested, no fix direction decided in advance.

  **Update 2026-07-18 (evening) — mechanism identified via logcat, the app fully exonerated.** The trigger was the follow-up report "with v0.6.0 there is no sound even after the volume key" (Spotify worked in parallel) — which turned out to be a **device-side ASHA volume state**, not an app regression (the audio code has been byte-identical since the last state confirmed working on 2026-07-13; the diff v0.5.0→v0.6.0 only touches theme and settings). The chain of evidence comes from two logcat transcripts (`adb logcat | grep bluetooth-asha`, see the implementation log):

  - **Mute state:** every playback is routed correctly to the hearing aid (`getOutputForAttrInt → AUDIO_DEVICE_OUT_HEARING_AID`, `checkAndSetVolume: index 15, volume 1.0, muted false` — everything on the AudioFlinger side turned all the way up), the hearing aid visibly acknowledges the stream (microphones mute, the duration correlates with the word length), but the ASHA `Start` command goes out with **`volume=0x80` (= −128 dB, ASHA mute)** → the hearing aid plays silence.
  - **After the author's fix** (the right channel switched on in the hearing aid's connection settings, "adjust volume separately" stayed off): identical playback → **`volume=0x0` (0 dB, full volume)**, the word fully audible (author confirmed, both channels).
  - **Which explains the volume-key pattern:** the key press sets an absolute volume in the system and thereby repairs the same ASHA volume state — same cause, different trigger. **Counter-check confirmed (author, same evening):** after the channel fix Spotify plays immediately without a volume-key press — the general, system-wide symptom disappeared with the same fix.
  - **Diagnostic signature for future sessions:** `SendStart: send Start cmd, volume=0x80` = ASHA volume state muted (fix on the device, not in the app); `volume=0x0` = healthy. A persistent `SendAudio: Playback stalled: cmd acked=false` across the whole playback = the ASHA control point is stuck (reconnecting the hearing aid may help).
  - **Side finding (no item of its own, an observation):** the stall window until `StartAudioCtrlCallback` (audio is discarded while the start command is unacknowledged) measured about 150–240 ms — the 180 ms pre-roll silence usually covers that, but not in the worst case. No current symptom (author: "fully audible"); should word-onset clipping return, raise the pre-roll (`BLUETOOTH_PREROLL_MILLIS` in `AudioSink.android.kt`) accordingly.

  **Note (ticked off 2026-07-18):** solved on the device side — switching on the right hearing-aid channel in the Android connection settings moved the ASHA volume state from `0x80` (mute) to `0x0`; AudioLex playback fully audible, and the counter-check shows that Spotify and friends play immediately again without a volume-key press too. The author's original question (waking the path from the app via `adjustStreamVolume(ADJUST_SAME)`) is therefore moot — there is nothing to fix on the app side; the diagnostic signature above stays as a reference should it ever return. No code change, no version bump (stays v0.6.0).

- [X] [P2] [Session] [→Sonnet] **Learning mode: shuffled order (fixed per session) plus "Previous" navigation.** Two related author requirements (2026-07-12, A53 device test), deliberately sharpened as **one** item because they touch the same `LearningSession` structure and "Previous" only makes sense with an order that is fixed for the session. (a) The corpus words should no longer be walked in file order but shuffled, so that the sequence of words is not what gets memorised instead of the words. (b) Next to "Next" there should be a "Previous" that steps one word **back** in the session — explicitly not at random, but the order last seen, in reverse.

  Note: shuffling deliberately stays outside the deterministic `LearningSession` — `LernmodusScreen` calls `words.shuffled()` once at session start, after which the order is fixed for the session; `LearningSession` itself still only knows a linear walk over the list it was handed. An additive `LearningSession.back()` (mirroring `advance()`, resets `repeatCount`, returns `null` on the first word) plus an `isFirstWord` property were added. `LernmodusScreen` gets a "Previous" button (disabled via `enabled = !session.isFirstWord`) next to "Next"; the existing auto-play keyed on `currentIndex` works unchanged when stepping back. 3 new `LearningSessionTest` cases (`back()` on the first word → `null`, `back()` from the middle, `advance().back()` returns to the start). `rate`/`advance` as well as `ExamSession`/exam mode untouched. `./gradlew build` green including `:core:jvmTest`.

  **Author's decisions (2026-07-12, gathered while sharpening):** (1) **Rolled once per session, then fixed** — every start of learning mode reshuffles the order once, and it stays stable for the duration of the session (next session → new order). (2) **Every corpus word exactly once** — the word list is permuted once like a shuffled deck, no word repeats within a session, so the finite end (`Finished`) and the progress display (`x / total`) stay meaningful unchanged.

  **Architecture (Opus):** shuffling does **not** belong in the pure `LearningSession` (which should stay deterministic and testable — no hidden `Random` in the constructor). Instead: the caller (`LernmodusScreen`) shuffles the loaded word list **once** at session start (`words.shuffled()`) and hands the already shuffled list to `LearningSession(words)` — the session keeps working on the order it was given (current behaviour, unchanged). For "Previous", `LearningSession` gets an additive `fun back(): LearningSession?` mirroring the existing `advance()`: steps back to `currentIndex - 1`, returns `null` when already on the first word (no wrap). `advance()` stays unchanged.

Symptom: in exam mode the word onset of the automatic first playback is clipped on practically every new card (sometimes less, sometimes clearly audible); tapping "Repeat" for the **same** card afterwards gives the full word — so the difference between "new card, automatic" and "same card, repeated manually" is the triggering pattern, not a general clipping bug.

  **Suspected root cause (a suspicion, not verified — no reproduction with measurement as with the PulseAudio bug):** `AndroidAudioSink.play()` (`core/src/androidMain/.../AudioSink.android.kt`) builds a completely new `AudioTrack` for **every** playback via `AudioTrack.Builder()...build()`, writes the whole buffer immediately (`MODE_STATIC`) and calls `track.play()` straight away. With Bluetooth output (here: the hearing aid, the ADR-0007 reference setup) the routing to a new `AudioTrack` is not instantly "hot" — an already running or just-active Bluetooth audio path (because the same track ran shortly before, say) comes through immediately, whereas a freshly created track risks losing the first milliseconds in the Bluetooth connection/codec warm-up before the stream actually reaches the hearing aid. A diagnostic log test already present in the code (added temporarily, removed again) showed a complete `write()` for two individual test clicks (30720/30720 shorts), `playState=3` (PLAYING) and a correct `routedDevice` — the data flow at the `AudioTrack` API level was unremarkable there; that rules out a gross app error such as a wrong buffer size, but does not point at the cause itself (the log did not capture a repeat with the same `AudioTrack` to check the "new versus repeated" distinction directly).

(b) Reuse the `AudioTrack` across a session instead of building a new one on every `play()` call (cache the instance in the sink, only `stop()`/write again/`play()` instead of `release()` plus rebuild) — this avoids the cold start per word, but changes the lifecycle (`close()` is currently a no-op and would then have to really release the cached track) and has to be aligned cleanly with the existing cancellation fix (ADR-0003, `play()` is `suspend` and reacts cooperatively to cancellation). (c) Warm up `AudioManager`/`AudioAttributes` deliberately (e.g. send a minimal silence frame as soon as the screen/card loads, before the actual word is due) — this couples sink behaviour more tightly to screen timing, more complexity. Probably only affects Bluetooth output (the reference setup); whether wired headphones or the speaker show the same is untested.

- [ ] [P3] [PROP] [Audio] **Masking the good ear during channel training** (an idea from the A53 finding 2026-08-06). In headphone training, channel separation runs into a physiological limit: a signal offered only to the weak ear is, above a certain level, heard along by the good ear (cross-hearing, with an interaural attenuation of only ~40–60 dB). So you unknowingly train the wrong ear. In audiometry the standard solution is **masking**: the good ear is given a noise to keep it busy. AudioLex would already have all the pieces for that — the noise overlay (ADR-0010) and the channel separation (`StereoGain`, ADR-0011); all that would be needed is to combine them on **separate** channels: speech on the left, noise on the right. That would be no new audio technique, just a rewiring of existing parts. Open and explicitly undecided: whether it makes sense in the subject matter and is comfortable for the author (masking levels want balancing) and whether it serves the training goal or complicates it. Assess only after batch B, once channel training has been tried for real.
- [ ] [P3] [PROP] [Corpus] **Export/import per contingent instead of all-or-nothing — and passing finished decks on** (author's proposal 2026-08-07). The backup from v0.26.0 deliberately knows only "all or nothing" (a non-goal of that item). Selectable per contingent, it would at the same time be a **format for passing things on**: "Grete speaks 200 everyday words" as one file that someone else can import. A kind of marketplace for decks could be built on that.

  **Why that is architecturally close at hand:** the archive format already carries it — one folder per content type, and a contingent export is nothing but a subset of the entries plus their WAVs. `readBackup` merges by ids and already skips what is known; importing someone else's deck is the same code path as restoring your own backup. The ids (`own-<timestamp>-<random>`, ADR-0012) are collision-resistant enough across devices that two sources do not get in each other's way.

  **What wants deciding beforehand:** (1) **The marketplace is not an app function.** AudioLex has no network permission and, per ADR-0013, should not get one — exchange means a file plus a place outside the app (a website, a repo, the user's cloud folder). That is consistent with the stance so far: the app writes a file, and what happens to it afterwards belongs to the user. (2) **Other people's voices are personal data.** A recording passed on carries the voice of an identifiable person; whoever publishes a deck needs their consent. Not a formality but the heart of the matter as soon as "my backup" becomes a distribution route. (3) Curation — a deck of unusable recordings is worse than none.

  **On the consent checkbox (author's proposal 2026-08-07, assessment by Opus — not legal advice):** rightly thought, but it belongs on the deck export, **not** on the backup, and it is an assertion, not a consent.

  - **Whoever clicks is not whose voice it is.** The person recording ticks the box, and the speaker never touched the device. The checkbox therefore produces an *assurance by the person passing it on* — exactly the model every platform uses that accepts third-party content, and sufficient for the app's side. But it does not replace the consent actually existing outside.
  - **Not on the backup export.** No third party is involved there, and ADR-0013 explicitly sets down for that route: no dialog, no cascade of warnings. A checkbox that appears on every backup gets clicked away and is worthless on the one occasion it counts.
  - **As a field in the archive, not only in the UI.** A tick that merely unlocks a button leaves no trace. The declaration (who, when, for which voice) belongs in the deck metadata, so that it travels with the file and is still checkable three hand-offs later.
  - **The text has to say what the click is** (author's decision 2026-08-07: "yes, record it that way"). Not "consent to publication has been given" — that claims the consent comes into being through the click. Rather along these lines: **"I confirm that I have the consent of the person recorded to pass this on."** First person, an assurance rather than a granting, and naming who it has to exist towards. It costs nothing and is the difference between a wording that carries and one that proves the opposite in a dispute. The final wording with the `prose-anti-ki` skill.
  - **What stays unsolved is withdrawal:** consent can be withdrawn, a distributed file cannot. No checkbox helps against that — but it argues for carrying the speaker's name and a way to make contact along, so that a withdrawal has an address at all.

  **Here "deck" earns its name** (see the terminology item below): what gets passed on is exactly what makes a deck — a bundle you select and train.
