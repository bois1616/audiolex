# ADR-0003: The audio pipeline — a shared PCM mixer, platform-specific output, a WAV corpus

- **Status:** accepted
- **Date:** 2026-07-07

## Context

The core requirements: per-channel control (left/right/both) with separate levels, a background-noise overlay with an adjustable signal-to-noise ratio (SNR), several target platforms. That logic has to be testable by an agent — that is, without an audio device, as a pure function over samples.

## Decision

1. **Mixing in common Kotlin:** channel gain (`StereoGain`), the noise mix and the SNR calculation (`noiseGainForSnr` over RMS) work on a `PcmBuffer` (interleaved PCM16) in `commonMain` — fully unit-testable on the JVM.
2. **Output as a narrow expect/actual interface `AudioSink`:** Android → `AudioTrack`, desktop → an external `paplay` process with a `javax.sound.sampled` fallback (see consequences), iOS later → `AVAudioEngine`. The sink receives finished mixed stereo PCM; no platform logic above the sink.
3. **Corpus audio format for the MVP: WAV (PCM16, 22050 Hz, mono):** no decoder needed, and a WAV loader of our own runs identically on all targets. 22050 Hz is the native output rate of the chosen Piper voices (ADR-0006) — no resampling step, no loss of quality. The mixer and `AudioSink` are sample-rate agnostic (they take the rate from the `PcmBuffer`); noise loops have to have the same rate as the speech recording in question, otherwise `mixWithNoise` fails (a rate check). Should higher-quality sources with a different rate arrive later (own recordings, another TTS), a resampling step is needed at corpus import — not in the core logic.

## Alternatives

- **A platform player (ExoPlayer/Media3, AVPlayer):** it takes file formats off our hands, but SNR mixing and sample-accurate channel control would have to be built twice, once per platform, and would hardly be testable headless. Rejected.
- **A compressed corpus (Opus/MP3) from the start:** it saves space but forces platform-specific decoders (MediaCodec/AVAudio) into the MVP already. Postponed — with a corpus in the hundreds of words, WAV is uncritical.

## Consequences

- The riskiest logic in the subject matter (levels, SNR) is tested deterministically; platform bugs can only sit in the thin sink.
- WAV files are about 10× larger than Opus; accepted for the MVP, and a codec switch stays possible later behind the loader.
- Latency is uncritical (single-word playback, no real-time monitoring) — `AudioTrack`/javax.sound suffice, Oboe/JNI are unnecessary.
- **A WSL2 quirk discovered (2026-07-08):** Java Sound (the ALSA backend) finds not a single audio line under WSL2 — `AudioSystem.getMixerInfo()` returns an empty list regardless of the sample rate. PulseAudio itself works (`paplay`/`pactl` through the WSLg RDP audio bridge), but Java Sound only speaks to ALSA directly. The desktop `AudioSink` therefore writes the PCM data into a temporary WAV file and calls `paplay` as an external process; `javax.sound.sampled` stays the fallback for environments without `paplay` on PATH (macOS, say, or a Linux desktop with a working ALSA setup). This concerns only the desktop dev sink — Android/`AudioTrack` is untouched by it. *(The environment turned out to be native Debian rather than WSL2 — author's correction 2026-08-17; the `paplay` route stays in place.)*
- **Android channel swap — the finding retracted (2026-07-07, re-tested 2026-07-08):** the side swap on the Galaxy A53 originally suspected on 2026-07-07 and "fixed" with `swapStereoChannels()` rested on contaminated evidence (Opus review 2026-07-07, finding 1: the original test had a channel that was silent by construction through `LEFT_ONLY = (1, 0)`, the system sound balance was unnoticed at right=0, and the Bluetooth mono summation made the "confirming" second test unfalsifiable). A clean re-test protocol on 2026-07-08 (the sound balance demonstrably reset to a shared volume, USB-C wired headphones instead of Bluetooth, a build with an explicitly switchable swap state, an earcup test: both headphone cups held to the good ear one after the other instead of trusting the impaired hearing) produced the opposite: **without the swap**, "left" came correctly out of the left cup and "right" correctly out of the right, with clean channel separation (no crosstalk). With the swap ON the result reversed as expected. The device was never faulty — `swapStereoChannels()` was itself the bug. The fix was rolled back: `AndroidAudioSink` no longer applies the swap by default; the function stays only as groundwork for a possible future "swap channels" user setting (backlog M4), and is no longer wired up.
- **`AudioSink.play` made a `suspend fun` — real cancellation instead of mere coroutine bookkeeping (2026-07-09):** while setting up M2's `PlaybackQueue` (session control, listening to a word again or cancelling it), it turned out that `play()` as a normal blocking function had no cancellation hook — `PlaybackQueue.stop()` or a new `play()` call did cancel the surrounding coroutine, but Android (`Thread.sleep`) and the desktop (a `paplay` process with `waitFor()`) played on to the end anyway, because cancellation cannot act cooperatively on a blocking, non-suspendable call. Fixed: `AudioSink.play` is now a `suspend fun`; Android waits with `delay()` (a cancellation point) instead of `Thread.sleep()` and calls `track.stop()` in the `finally`; the desktop uses `runInterruptible { process.waitFor() }` plus `process.destroy()` in the `finally` (and likewise for the `javax.sound` fallback: `runInterruptible` around `line.write`/`line.drain()`). Verified with a temporary test case that was deleted afterwards: `job.cancel()` + `join()` ended an externally running process in 45 ms instead of waiting out the remaining ~2.7 s, and the process demonstrably no longer wrote a "finished" marker. Without this fix, S2 ("listen to a word again") and S5 ("leave a session cleanly") would not have held in the real app what their scenario descriptions promise.
